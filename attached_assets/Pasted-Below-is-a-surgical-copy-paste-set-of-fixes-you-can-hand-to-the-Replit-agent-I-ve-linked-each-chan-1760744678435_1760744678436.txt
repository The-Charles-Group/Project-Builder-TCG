1) Step 2 — L2 not showing after “Apply Smart Selection” (and needing two clicks)

Root cause: The server’s compatibility wrapper only accepts selected_l3_map / selectedL3Map / l3Map. Your UI now sends L2 keys (selectedL2Map / l2Map). The map is dropped server‑side, so L2s vanish after the “Apply Selected to Manual Selection” hop.

Fix (server): In api_post_scenarios (the Step‑3 builder wrapper), extend the accepted names so L2 keys are treated as synonyms for the old L3 keys.

# in api_post_scenarios(...)
selected_l3_map = (
    payload.get("selected_l3_map")
    or payload.get("selectedL3Map")
    or payload.get("l3Map")
    or payload.get("selected_l2_map")
    or payload.get("selectedL2Map")
    or payload.get("l2Map")
)


This is the same function that already normalizes other field names on the Brad build (see the multiple “*_codes” variants). Add the three L2 variants where selected_l3_map is parsed. You’ll find the block in the Brad doc under the /api/scenarios POST wrapper that logs “Found codes in field…” and normalizes fields.

Why this removes the “two clicks” quirk: the first click was queuing L2 in the UI, the second re‑derived tasks by clicking a component (client‑side fallback). Once the server actually ingests selectedL2Map/l2Map, the L2 column can populate on the first pass.

3) Step 3 — Build Scenario works, but pricing table empty and Grand Total shows $0

Root cause A (wrong endpoint/shape):

The Brad update consolidated the scenario builder to POST /api/scenarios. It does not return total_price / total_hours at the root like older code; it nests totals under the scenario, so your current UI (which still expects the old root fields) shows $0. The new wrapper is in place (and very tolerant about field names) but the top‑level totals aren’t emitted.

Quick compatibility fix (server): After assembling scenarios, also include top‑level totals for the “A” scenario so the existing UI sees numbers again:

# At the end of api_post_scenarios(...)
result = {"scenarios": scenarios}
a = scenarios.get("A") or {}
totals = a.get("totals") or {}
result["total_hours"] = totals.get("hours", a.get("total_hours", 0))
result["total_price"] = totals.get("price", a.get("total_price", 0))
return result


This preserves the new shape and satisfies the legacy UI’s expectations.

Root cause B (components not listed in pricing table):
Ensure each scenario item carries its included components and task groups so the editable table can render them. The builder already supports component‑level hours and backfills deliverable defaults when a component selection sums to 0 (so you don’t end up with zeroed deliverables). Confirm you’re passing selected_components_map (or its camelCase variants) in the POST; the wrapper already supports those names.

5) Step 4 — Timeline “request timeout” / loop

Root cause: The Brad update made timeline generation asynchronous with job tracking. The endpoint now returns a job_id immediately and expects the front‑end to poll a status route (or attach to an SSE stream) until it’s done, then read the result. That’s why you’re seeing a timeout banner even though the server is working in the background. The new job‑status alias is /api/agencydb/status/{job_id}.

Fix (front‑end logic):

POST /api/ai/generate_timeline → capture job_id from the JSON (success: true, job_id: "...").

Poll GET /api/agencydb/status/{job_id} every ~1–2s until status is completed, then take data for the Gantt chart. The alias returns progress %, stage message, and—when complete—the actual deliverables/tasks.

If you want a quick synchronous fallback (no polling), you can also expose a POST /api/timeline/generate_sync that awaits the same worker and returns the full timeline in one response.
