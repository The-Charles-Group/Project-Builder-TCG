🔧 Root causes & fixes
1) Retainer mode can zero‑out hours

Symptom you see: turn “Use retainers” on → build → both panels show 0 hours / $0.
Why: when the server builds each deliverable it multiplies “monthly hours” by months. If the client sends months: 0 (or the field is present but blank), total becomes 0 × monthly = 0. You want “0 months” to mean “treat as one‑time (non‑retainer)”, not “zero out”.
Fix: inside the scenario builder, compute total_hours like this:

# inside _scenario_for_deliverable(...)
months = max(0, int(retainer_months or 0))  # tolerate '', None
monthly_hours_int = int(round(sum(hours_by_role.values())))
total_hours = monthly_hours_int if months == 0 else monthly_hours_int * months
out = {
    # ...
    "monthly_hours": monthly_hours_int,
    "total_hours":  total_hours,   # one-time if months==0, otherwise monthly * months
    # ...
}


Why this patch: the scenario builder’s output comment literally says the field is “total (months × monthly)”—the code needs the “months==0 means one‑time” escape hatch to avoid wiping the totals when the user hasn’t typed months yet.

If you’d rather force months to be ≥1 whenever retainers are on, clamp in the payload parser instead: months = max(1, min(12, int(r.months))). But most folks expect “left blank” to behave like one‑time.

2) When you rebuild in Step‑3, the API isn’t guaranteed to receive component selections

Symptom you see: “Proceed to pricing” sometimes shows numbers, but clicking Build Scenarios A & B after toggling retainers drops to 0 hours/$0.
Why: if included_task_groups for a deliverable is missing/empty, the DB query that produces hours by role returns an empty table → 0 hours. (The helper returns an empty DataFrame when the deliverable has no included task groups.)

There is already a defensive helper _inflate_components_if_missing() that auto‑fills all task groups from the DB when selections are absent so scenarios “never go flat.” Call it on every scenario right before totals/pricing and again in export.

Backend patch (FastAPI):

# wherever you assemble a scenario dict (A, B, C, auto-build, export):
scenario_out = _inflate_components_if_missing(scenario_out)   # <— add this line


This guarantees rebuilt scenarios still have components even if the Step‑3 payload didn’t carry them.

Frontend patch: always include what the user selected in Step‑2 when you hit /api/build from Step‑3.

// Build Scenarios A & B click handler
const payload = {
  pricing_mode:  $('#pricing-mode').value,
  blended_rate:  parseFloat($('#blended-rate').value || 0),
  rate_band:     $('#rate-band').value,
  complexity:    $('#complexity').value,
  volume_tier:   $('#volume-tier').value,
  project_name:  $('#project-name').value.trim(),
  selected_deliverable_codes: Array.from(selectedCodes),
  // send component selections too
  selected_components_map: Object.fromEntries(
    Array.from(selectedCodes).map(code => [code, Array.from(selectedComponents[code] || [])])
  ),
  use_retainers: $('#use-retainers').checked,
  retainers: $('#use-retainers').checked
    ? Object.entries(retainerMonths).map(([code, months]) => ({
        deliverable_code: code, months: +months || 0
      }))
    : []
};


Why this matters: without included_task_groups, hours_by_role_for_deliverable(...) receives an empty list and returns zero rows → 0 hours.

3) “Flat” XML after using AI suggestions

Symptom you saw earlier: XML uploads with only top‑level deliverables (no components/indentation) when the items came from the AI column.
Why: same missing‑components issue during export. The export route builds a WBS DataFrame and you want it to inflate components before converting to XML. The code path that generates the Excel used for XML should use the same _inflate_components_if_missing() helper.

Backend patch:

Wherever build_wbs_dataframe_from_scenario(...) is called for export, make sure its first line inflates:

def build_wbs_dataframe_from_scenario(scenario: dict, project_name: str) -> pd.DataFrame:
    scenario = _inflate_components_if_missing(scenario)  # <- ensure not flat
    return build_wbs_with_pricing(scenario, project_name)


(If you already call _inflate_components_if_missing inside build_wbs_with_pricing, you’re covered—just double‑check.)

🧩 Two quick UI regressions to fix
A) Duplicated options in Pricing mode and Rate band

The server returns unique lists; the duplicates come from repopulating the <select> without clearing it. Before appending, clear innerHTML.

function populatePricingOptions(opts){
  const pm = $('#pricing-mode'); pm.innerHTML = '';
  const rb = $('#rate-band');    rb.innerHTML = '';
  opts.pricing_modes.forEach(v => pm.append(new Option(v, v)));
  opts.rate_bands.forEach(v   => rb.append(new Option(v, v)));
}

B) “Project name” should auto‑fill from the uploaded file

Your export code already defaults to the upload title on the server (via _upload_title_default()), so mirror that in the UI: as soon as a file is chosen in Step‑1, set the Step‑3 input.

$('#rfpFile').addEventListener('change', e => {
  const n = (e.target.files?.[0]?.name || '').replace(/\.[^.]+$/, '');
  if(n) $('#project-name').value = n;
});


You can also keep the server default as a back‑stop—api_export_xml uses exactly that default today.

🧱 “What you see in Steps 2–4 is what you export”

To make that iron‑clad:

Always pass both selected_deliverable_codes and the selected_components_map to every build/export route (see the Step‑3 payload snippet above).

Call _inflate_components_if_missing() server‑side so an empty client map can’t produce a “flat” outcome.

The hours math uses the DB “scenario hours” column derived from complexity+tier; if included_task_groups is empty, the DB function returns an empty frame (0 hrs). This patch prevents that edge case.
