Below is what I recommend, in order of safety.

1) Make code‑based matching mandatory (preferred)

Generate deterministic codes for any component/task that lacks one (e.g., slug of the name + stable hash) before you build the WBS DataFrame. Then merge by codes only.

If any component/task still has a null code at export time, fail the build and print a clear report (deliverable, component name, task name).

Why: Names are brittle (punctuation, spacing, rewording) and a silent name match can mis‑merge hours/dates. Codes are stable.

Why this matters right now: Your latest XML schedules the project from start (11/17) and uses a standard Mon–Fri calendar with holidays; if a task’s timeline values don’t merge, it arrives with ASAP default behavior and shifts to 11/17. That’s consistent with your file header.

2) If you must ship today: add a strict, visible name‑based fallback (tasks only)

If a code is missing:

Match only leaf tasks by (deliverable_code + component name + task name), after normalizing (lowercase; strip punctuation/whitespace; collapse spaces; remove “&” vs “and” variation).

Only accept the match if it’s unique inside that deliverable+component. If more than one candidate matches, do not merge—emit a warning row in an “unmatched.csv”.

Never apply name fallback to components (too much ambiguity). If component_code is missing, either:

generate a component_code from component name up‑front, or

require the user to pick from a list; don’t guess.

This gets you working results without risking silent, wrong merges.

3) Guardrails that prevent “everything starts Nov 17” again

Add these to the exporter now, independent of the merge strategy:

Write SNET for tasks that have explicit start dates.
For every leaf task with a start_date after merge, emit:

<ConstraintDate>YYYY-MM-DDT09:00:00</ConstraintDate>
