1. What the different “days” actually mean

For the Brand Identity Development chunk in your app:

300 hours effort

Effort days @ 8h/d ≈ 38 days → purely hours / 8. This is “how many full‑time days of work if one person did it.”

Span: 88 calendar days (2026‑01‑05 – 2026‑04‑02) → difference in calendar dates (Mon–Sun).

Working duration (Mon–Fri): 64 days → number of business days (Mon–Fri, no weekends) between 1/5 and 4/2.

Your app’s tooltip is using that last value (64 working days), which is correct.

Workfront’s Duration column is also a working‑days number – but for a summary task (like “Brand Identity Development”) it is computed from its children: earliest child start → latest child finish, using the project calendar.

So to make everything match, three things must all line up:

The Step‑4 Gantt schedule (what you see in the app).

The MSPDI XML (Duration + Start/Finish for the tasks).

What Workfront calculates from those child tasks.

Right now #1 and #2 are close, but #3 is still reading a shorter span from the child tasks, so Workfront shows 25 days.

c) Why Workfront still shows ~25 days

Workfront treats “Project Summary” and “Brand Identity Development” as summary tasks with ~113 children beneath them (you’ve just got the view collapsed).

For summary tasks:

Workfront ignores the Duration value from the XML.

It recomputes Duration as the span between earliest child start and latest child finish, using the Mon–Fri calendar.

In your code, when you compress deliverables, there’s a special “no shift” path:
