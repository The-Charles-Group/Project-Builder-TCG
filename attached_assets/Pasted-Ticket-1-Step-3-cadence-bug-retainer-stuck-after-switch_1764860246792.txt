Ticket 1 – Step 3 cadence bug (retainer stuck after switching back to one‑time)

Problem (user‑visible)
In Step 3 Pricing:

Open Step 3 → Pricing.

Edit a deliverable (example: Brand Positioning Strategy).

Change cadence to Monthly with 12 units, click Save.

Edit the same deliverable again, change cadence back to One‑Time, clear the units, click Save.

Click Build Scenario.

In Deliverable Pricing Details, that deliverable is still treated like a Retainer (type or label shows Retainer / Months > 0) even though cadence is now One‑Time.

Technical root cause (high level)
The pricing helper apply_cadence_to_item(new_item, old_item=None) recomputes totals when cadence changes, but:

It sets retainer, retainer_months, monthly_price, monthly_hours when is_retainer is True.

It never clears those fields when the cadence is changed back to one_time.

So once a deliverable has ever been a retainer, the scenario item keeps non‑zero retainer_months and retainer metadata, and downstream code (Deliverable Pricing Details + WBS/XML) continues to treat it as a retainer.

What I want changed

In apply_cadence_to_item, after computing is_retainer and total_months, add logic that:

When is_retainer is False (e.g. cadence is one_time OR total_months is 0), explicitly reset all retainer‑related fields on the item:

retainer = {}

retainer_months = 0

monthly_price = 0

monthly_hours = 0

When is_retainer is True, keep the current behavior, but ensure:

retainer["months"] and retainer_months are both set to int(total_months).

Keep the existing priority rules intact:

PM override via monthly_price (if changed) should still win.

Otherwise, use cadence_price and cadence_units to derive total_price.

Keep price_usd, Price_USD, and total_price in sync.

Use get_rate_from_item + get_price_from_item to derive total hours and call set_hours_on_item.

Make sure monthly_hours is only non‑zero when the item is currently a retainer:

monthly_hours = total_hours / total_months when is_retainer and total_months > 0

monthly_hours = 0 otherwise.

Suggested patch shape (pseudo‑code)

In apply_cadence_to_item after is_retainer and total_months are known and before computing hours:

# Persist / clear retainer metadata
if is_retainer and total_months > 0:
    new_item["retainer"] = {**existing_retainer, "months": int(total_months)}
    new_item["retainer_months"] = int(total_months)
else:
    # Item is no longer a retainer – clear all retainer state
    new_item["retainer"] = {}
    new_item["retainer_months"] = 0
    new_item["monthly_price"] = 0
    new_item["monthly_hours"] = 0


Then continue with the existing rate/price/hours calculation and the existing if is_retainer and total_months > 0: monthly_hours = ... else: 0 block.

Ticket 2 – Change “Months” column in Deliverable Pricing Details to “Hours”

Current behavior

In the Step 3 Pricing screen, under Deliverable Pricing Details, there’s a table showing:

Deliverable name

Type (One‑Time / Retainer)

Rate / Price

A “Months” column (from retainer_months in the backend)

For what we’re doing now, “Months” isn’t very helpful at the summary level – we’d rather see hours per deliverable in that slot.

The backend breakdown endpoint already computes hours per deliverable in its summary structure, alongside rate, price, cadence, months, etc. (endpoint is something like /api/pricing/rebuild_breakdown or similar – it’s used by Step 3 to populate Deliverable Pricing Details).

What I want changed

Front‑end only (unless you discover the backend doesn’t expose hours – in that case, expose it as described below):

Rename the column:

In the UI component that renders Deliverable Pricing Details (Step 3 Pricing):

Change the header text from “Months” to “Hours”.

Change the data bound to that column:

Instead of showing months / retainer_months, show the total hours for the deliverable.

The backing API response already includes a field named hours per deliverable summary row. Bind the column to that hours field and format as a number (integer is fine; round as needed).

Keep cadence/type information elsewhere:

Do not remove the “Type” or “Cadence” indication (One‑Time vs Retainer). Those still tell us that something is a retainer.

We’re only swapping the Months column for Hours in this particular grid.

If backend hours are missing (fallback instruction)

If the breakdown endpoint doesn’t currently expose hours:

In the endpoint that prepares the Deliverable Pricing Details rows (the one returning deliverable summaries):

For each deliverable, sum the item‑level hours (using the same helper used elsewhere, e.g. get_hours_from_item / scenario items).

Write that value into a new field hours on the deliverable summary object.

Keep the existing months field for backwards compatibility, but the front‑end should stop using it in this table.

Acceptance tests

Build any scenario (mix of One‑Time and Retainer deliverables).

Open Step 3 Pricing → Deliverable Pricing Details.

Column header previously labeled “Months” now reads “Hours”.

The values in that column are numeric hours (e.g., 98, 109, etc.), matching the per‑deliverable hours shown in the main scenario totals.

The “Type” / “Cadence” indication still correctly shows One‑Time vs Retainer and is unaffected by this change.

Spot check:

Pick a deliverable, sum its underlying rows’ hours in the main pricing grid. The Hours value in Deliverable Pricing Details for that deliverable should match (or be off by at most rounding).
